# MunServ v1: definition of done

This file says what v1 holds and how each part passes. It comes from the interrogation brief of 2026-11-05 (plan step S25): https://claude.ai/artifact/AvxFR6nYuMstBvSKtLD28i. The `Q` numbers in the Source columns are that brief's questions.

`M1` to `M10` here are plan milestones. They are not the mobile story ids in `mobile.md`, which use the same letter.

## The shape of v1

The outer edge is decision D1: the full ward stack in one pod. v1 follows the plan's order and depth (Q12, Q18), and it has two gates.

- **Demo gate.** Every exit in M1 to M10 passes, except the funded parts. The project owner shows the system alone, from the laptop, with invented data.
- **Pilot gate.** Every funded part passes, and a community has agreed. Plan step S36 starts then.

A funded part waits on money or a named person. Every other exit can pass without either. No one pays for a host today (Q15), and no community exists (Q01). The discussions after the demo decide what follows.

## Email

Email carries only what a person cannot do in the app while logged out or not yet a member. All else is push or a message (Q13).

| Event | Why the app cannot reach them | In v1 |
|-------|-------------------------------|-------|
| Member approved | The person has no password yet. | Email stays. The approval response stops carrying the password. |
| Pod chief created | The person has no password yet. | Email stays. The bootstrap response stops carrying the password. |
| New admin created (m16) | The person has no password yet. | New email. The API response and the portal dialog stop carrying the password. |
| Registration rejected | The person never becomes a member. | New email. |
| Password forgotten | The person is logged out. | New email, with a one-time token. |
| Member suspended or reinstated | Login refuses a suspended member, so a message stays unread. | Two new emails, one per event. |

## Milestones and exit criteria

### M1 · Security and photo integrity (S27)

- The curl matrix passes on master: anonymous 401, stranger 403, no EXIF in a download.
- The app refuses to start without `JWT_SECRET` outside local, and auth endpoints answer 429 past their limit.
- An admin outside the sector gets 403 (#254), a member cannot create an issue in another sector (#257), and verification outcomes write audit rows (#255).

Needs: nothing outside the code.

### M2 · Photos that survive (S28)

- In airplane mode, a report with 3 photos queues, and all 3 land within 60 seconds of reconnecting on a real phone.
- A retried photo creates no duplicate.
- With no signal, the member opens their own issue list from the cache, and it shows the time of the last sync.
- When the server refuses a queued report (#257), the member sees the reason and can correct the report.
- Thumbnails are real files (#105), and photo URLs come from a configured base URL.

Needs: nothing for the build, which uses the S3 interface. A budget sets the production store: AWS and Z1 Storage take that interface, and a VPS volume does not.

### M3 · Fast first visit (S29)

- CI prints the budget table on every PR: initial route at 200 KB gzip or less, dashboard LCP at 2.5 s or less, CLS at 0.1 or less on a mobile profile.
- Issue and member lists page in SQL.

Needs: nothing outside the code.

### M4 · Wards, sectors and boundaries (S30)

- A fresh pod reaches setup complete from an empty database through the portal alone, drawing its boundaries there.
- A ward admin acting on a sector outside the ward gets 403 (#56).

Needs: nothing outside the code.

### M5 · Launch infrastructure (S31)

- Demo part: the showcase stack answers over the VPN, and a phone on the VPN reports an issue with an APK built for it.
- Demo part: a script resets the stack to invented data, and the stack holds no real resident's data.
- Demo part: the project owner can read account email from their phone during the demo.
- Funded part: the Play build calls the API over HTTPS, and the app's API address no longer hard-codes http.
- Funded part: a tagged release deploys to the chosen host in South Africa.
- Funded part: an Android build reaches the Play closed track, and its opt-in link installs on a real phone. No iOS build.
- Funded part: the restore drill log on master shows a restored database and its duration.
- Funded part: an error-rate alert and an uptime check fire in a test.
- Funded part: account email leaves through the production path.

Needs: the project owner's sudo to install `cloudflared` on the laptop. For the funded part: a budget, which also closes AWS against SA VPS, and a Play developer account.

### M6 · Privacy pack (POPIA) (S32)

- Code part: member export and erasure work end to end, and consent stores its version at registration.
- Code part: the processor checklist names the host, the mail provider, Google Play's tester lists, FCM, OSM tiles, Nominatim and Google Fonts. Each has a status and a s72 ground column, marked open until the lawyer reads it.
- Code part: the notice text slot makes no promise of South African storage.
- Funded part: a lawyer has reviewed the notice in three languages, and the s22 procedure names the eServices portal and email to each member's address.
- Funded part: the responsible party has signed any s21 contract, and the information officer is registered.

Needs: a sponsor and a responsible party for the funded part.

### M7 · Accessible, in three languages (S33)

- Axe reports 0 serious violations on every route.
- A CI check fails when a key is missing in English, Afrikaans or isiZulu, on web, mobile and server text.
- Mobile's hard-coded strings are gone, and server messages and emails use the recipient's language.
- Funded part: a named reviewer has signed off Afrikaans and isiZulu.

Needs: reviewer names for the funded part. A pilot that speaks isiXhosa adds a fourth language.

### M8 · Messages by push, and email for account access (S34)

- Message types for an issue state change and for a new issue exist in the domain folder and the database, and both fire.
- Every kept type reaches the right recipient: #265 is closed, and `member_registration` has a caller.
- A state change reaches a test phone by push within 60 seconds, from the laptop stack, and a member who opted out receives nothing. The app asks for `POST_NOTIFICATIONS`.
- `verify_new_issue` and `verify_fix` reach a ground admin's phone by push, and m05 to m08 follow the same channel.
- Admin rows land in the portal inbox, and no message type sends admin email.
- A monthly job sends `monthly_report` in-app to each chief for their level, carrying issues fixed that month.
- Member welcome and pod chief welcome keep their email.
- A new admin gets the temporary password by email, and no API response or portal dialog carries a temporary password.
- A rejected applicant gets an email that says so.
- `EmailService` has no caller outside the account events in the email table.
- A logged-out member or admin resets a forgotten password by email, from the app or the portal. The token works once and expires, and an unknown address gets the same reply as a known one.
- A sector admin suspends and reinstates a member in their own sector, and each event sends an email. An admin outside the sector gets 403.
- A suspended member's next API call and next token refresh are refused, and a suspended ground admin loses the role through the revoke path.

Needs: nothing outside the code.

### M9 · Ward and sector dashboards (S37)

- Each of the six admin roles lands on a non-empty dashboard for its own area (#136), holding every panel d01 to d12 for its level, with issues fixed this month on top.
- A ward admin sees only their ward, and the server answers 403 for another ward's data, including `/admin/dashboard`.
- Average days to fix shows a real number (#55).
- A sector admin merges a duplicate report: `reportCount` rises, heat adds 5 up to the cap of 100, and the hottest list reorders.
- The merged report's member gets push when the main issue changes state, and r01 counts no rejection for the merge.

Needs: nothing outside the code.

### M10 · Reports for pod, ward and sector (S38)

- All three scopes show non-empty tabs from seed data, with issues fixed a month (r01) built first, and #109 is closed.
- A sector admin's request for another sector's report answers 403.
- Rows r01 to r08 appear, each number checked against a hand-counted seed.
- Member status history starts recording at the migration, and r03 leaves earlier months blank.
- No export, no PDF, no monthly email and no ground admin rate ship. #57 goes on the after-v1 list.

Needs: nothing outside the code.

## Gate checks

### Demo gate

- Every exit in M1 to M10 passes, except the funded parts.
- With invented data and over the VPN, each of the eight roles does its own job end to end: member, ground admin, sector admin and chief, ward admin and chief, pod admin and chief.

### Pilot gate

- Every funded part passes, and a community has agreed.

## What reopens a decision

- A named viewer or a date before M8 is done: build S30, S34 and S37 ahead of S27 and S28. M1 must still pass before any real data arrives.
- A viewer who wants to use the demo themselves: each person needs a Cloudflare client, an APK and an account, and Cloudflare's plan terms need reading.
- A budget below the AWS bill: take the SA VPS, and rewrite S31 for pgBackRest.
- A lawyer's reading of s72, or a sponsor who changes the responsible party: M6's notice and processor list change. A municipality also adds procurement.
- A community that speaks isiXhosa: M7 gains a fourth language.
